> 最后更新：2026-11-22

## 零、一句话

**插件对所有人开放 → 谁都能保、能报、能看自己；够 2T 且持续 7 天自动进候选池 → 组长点一下授予才开始算考核和奖励；每月保够 5/6 才发岗位奖励；连续 2 月不达标清退、3 个月内不得再申请；按档位保满 18–36 个月退休，权益与在岗完全相同，只是不再有义务。**

---

## 一、三个层次（最容易混的地方）

保种组涉及三件不同的事，分开看就不乱：

| 层次 | 是什么 | 谁决定 | 状态 |
|---|---|---|---|
| **① 插件能力** | 能不能保种、能不能上报 | **有 API Key 即可，任何人** | ✅ 0.3.0 |
| **② 岗位身份** | 算不算正式成员（有考核、有奖励） | **组长/admin 授予** | ⏳ 待做管理页 |
| **③ 权益** | 在岗与退休拿什么 | **组成员资格** | ✅ 已上线 |

**① 全开放，② 人工审核，③ 靠资格。** 三级递进，互不冲突。

## 二、角色与权限矩阵

| 角色 | 谁能进 | 保种 | 上报 | 看自己 | 考核/进度 | 看所有人 | 授予/撤销 |
|---|---|---|---|---|---|---|---|
| 普通会员 | 注册 | ✅ | ✅ | ✅ | ❌ | ❌ | ❌ |
| **保种参与者** | 开插件 + 覆盖 ≥2T | ✅ | ✅ | ✅ | ❌ | ❌ | ❌ |
| **保种组成员** | 组长/admin 授予 | ✅ | ✅ | ✅ | ✅ | ❌ | ❌ |
| 工作组-组长 | 站点任命 | ✅ | ✅ | ✅ | ✅ | ✅ 全部 | ✅ |
| admin | — | ✅ | ✅ | ✅ | ✅ | ✅ 全部 | ✅ |
| 养老成员 | 退休自动 | ✅ | ✅ | ✅ | 只读 | ❌ | ❌ |

**要点**：参与者和成员在**插件行为上完全一样**，区别只在站点是否给他记考核。所以普通人先保着，够 2T 后组长点一下，**不用重配插件**。

## 三、生命周期

```
[1] 任何会员填 API Key → 开启保种组（插件不检查头衔）
        ▼
[2] 选档位，开始保种（最小 2T）
        │
        ├─ 覆盖 < 2T ────────────→ 仅"参与者"，不记考核
        ▼
[3] 覆盖 ≥ 2T 且持续 7 天 → 自动进「待授予」候选池
        ▼
[4] 组长 / admin 点「授予工作组-保种」
        ▼
[5] 正式成员 → 下个自然月起累计退休进度与岗位奖励
        │
        ├─ 每月达标 → progress += 1/退休月数，发当月奖励
        ├─ 单月未达标 → 第 1 次提醒（不清退）
        └─ 连续 2 个月未达标 → 清退，3 个月内不得再申请
        ▼
[6] progress 累计到 100% → 退休 → 自动移入「养老」组
        ▼
[7] 养老成员：权益与在岗完全相同，不再有月度义务
```

## 五、月度考核（🔧 代码已有，`internal/seedgroup/standing.go`）

### 达标线

```
当月「覆盖达标」的累计时长 ≥ 当月自然时长 × 5/6
```

- 只累计**覆盖达标**的相邻上报区间
- **单段 7 小时封顶**（防长时间不上报后补报刷时长）
- 服务端自己算 `server_on_target`，**不采信插件结论**
- 只有 `is_staff=1`（正式成员）的行参与统计

### 未达标后果

| 连续未达标 | 处理 | 字段 |
|---|---|---|
| 第 1 个月 | 站内提醒，不清退 | `warned_at` |
| 第 2 个月 | **移出「工作组-保种」** | `evicted_at` |

**清退后 90 天内不得再申请**（硬门禁，候选池直接过滤）。

### 防作弊

| 异常 | 判据 |
|---|---|
| `no_clients` | 有客户端快照但一台都读不到（掉线） |
| `covered_drop` | 客户端可读、覆盖却掉一半以上 |
| `covered_jump` | 体积涨 3 倍以上且最老那颗做种时长没前进 |
| `impossible_rate` | 增速超阈值 |
| `on_target_mismatch` | 插件报的达标结论与服务端不符 |

**只呈现在 `anomalies` 字段给组长看，不自动处罚。**

## 七、岗位奖励（❓ 公式已设计，待拍板倍率）

### 先看问题：做种积分几乎没有区分度

站点现有做种积分公式（`internal/seedingbonus`）：

```
A = Σ[(1−10^(−Ti/4周)) · Si · (1+√2·10^(−(Ni−1)/6)) · Wi]
B = B0 · (2/π) · arctan(A / L)        官方种 B0=240, L=2400（每小时上限 240 瓶盖）
```

实测各档位（做种满 8 周、独种）：

| 档位 | 体积 | 做种/天 | 做种/月 | 占日上限 |
|---|---|---|---|---|
| 2T | 2,048 GiB | 4,088 | 122,651 | 71.0% |
| 5T | 5,120 GiB | 5,050 | 151,495 | 87.7% |
| 10T | 10,240 GiB | 5,402 | 162,047 | 93.8% |
| 15T | 15,360 GiB | 5,521 | 165,618 | 95.8% |
| 20T | 20,480 GiB | 5,580 | 167,411 | 96.9% |

**2T → 20T：体积涨 10 倍，做种收益只多 37%**（arctan 饱和）。

**所以岗位奖励必须陡峭**，否则没人愿意保大档。

### 公式

```
月奖励 = 基准 × 档位倍率 × (1 + 连续加成) × 预算缩放系数
```

| 参数 | 建议值 | 说明 |
|---|---|---|
| **基准**（2T 满月） | **122,651** | = 2T 的做种收益，让岗位与做种等重 |
| **档位倍率**（**体积线性**） | 2T=1.0 / 5T=2.5 / 10T=5.0 / 15T=7.5 / 20T=10.0 | 体积翻倍 → 奖励翻倍 |
| **连续达标加成** | 每连 3 月 +5%，上限 +30% | 鼓励长期在岗 |
| **月预算上限** | `0`（不限）或指定值 | `0` 时不做缩放；>0 时超预算全员等比削减 |

### 档位奖励表（未触发缩放 + 无连续加成）

| 档位 | 岗位/月 | 做种/月 | **合计/月** | 相对 2T | 岗位占比 |
|---|---|---|---|---|---|
| 2T | 122,651 | 122,651 | **245,302** | 1.00x | 50% |
| 5T | 306,628 | 151,495 | **458,123** | 1.87x | 67% |
| 10T | 613,256 | 162,047 | **775,303** | 3.16x | 79% |
| 15T | 919,884 | 165,618 | **1,085,503** | 4.43x | 85% |
| 20T | 1,226,512 | 167,411 | **1,393,923** | **5.68x** | 88% |

**设计目标**：10 倍体积 → **5.68 倍总收益**（旧方案只有 3 倍，被否掉）。

### 连续加成后的上限

| 档位 | 满加成（+30%）月奖励 | 年化 |
|---|---|---|
| 2T | 159,447 | 1,913,359 |
| 20T | 1,594,466 | 19,133,590 |

### 通胀量级（站收入约 237 万/月）

| 成员数（平均档位） | 月支出 | 占站收入 |
|---|---|---|
| 3 | 191 万 | 81% |
| 5 | 319 万 | 135% |
| 10 | 638 万 | 269% |
| 20 | 1,276 万 | 538% |

**口径**：工作组由审核控制，人数天然受控，所以默认**不设硬上限**；需要收口时把 `monthly_budget_cap` 设成正数即自动等比缩放。

### 为什么不用上传量、不常发邀请

| 选项 | 判断 | 原因 |
|---|---|---|
| **瓶盖** | ✅ 主用 | 最灵活，不冲击分享率经济 |
| 上传量 | ❌ 不用 | 白送流量，破坏 ratio 体系，无法回收 |
| 邀请名额 | ✅ 只作权益 | 已并入 13 项权益（无限），不单独做月度奖励 |

## 八、权益（✅ 已上线，两组完全对齐）

### 现行权限包：**13 项**

```json
[
  "download.billing.exempt",   // 下载不计量
  "ratio.exempt",              // 免分享率考核
  "hr.exempt",                 // 免 H&R
  "seedbox.limit.exempt",      // 免盒子数量/并发限制
  "seedgroup.self",            // 查看自己的保种数据
  "torrent.download",          // 下载
  "torrent.upload",            // 发种
  "forum.reply.create",        // 论坛回复
  "forum.topic.create",        // 论坛发帖
  "request.create",            // 求种
  "image.upload",              // 图片上传
  "points.rules.read",         // 读积分规则
  "invite.create"              // 发邀请（数量不限）
]
```

### 在岗与退休：**完全相同**

| | 在岗（staff-seed） | 退休（retire） |
|---|---|---|
| 权限 | **13 项** | **13 项（完全相同）** |
| 每月保够 5/6 | **必须** | 不必 |
| 月度瓶盖奖励 | 拿 | 不拿 |
| 退休进度 | 在攒 | 已满 |
| 头衔 | 工作组-保种 | 养老 |

**语义**：在岗和为站点做过贡献的人享有**同样待遇**，区别只剩「还要不要每月履约」这一事实。

### 邀请为什么是"无限"

不需要配限额。`internal/identity/invitations.go:979`：

```go
days, units := effective.Limits.InvitePeriodDays, effective.Limits.InvitePeriodUnits
if days == nil || units == nil || *days == 0 || *units == 0 {
    return nil    // 不做周期限制
}
```

`rc_site_groups.limits` 的三个 `invite_*` 全为 `null`，所以给权限即无限。

### 不给的东西（以及为什么）

| 权限 | 为什么不给 |
|---|---|
| `apikey.use` | 唯一用途是铸 key 驱动 automation 面；保种不写脚本，只增加泄露面 |
| `torrent.review` / `user.ban` / `forum.manage` 等 | 保种是执行岗，不是管理岗 |
