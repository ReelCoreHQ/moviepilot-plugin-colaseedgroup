# 可乐PT 保种组 · 完整设定

> 版本 **v0.5.0** ｜ 2026-11-22 定稿
> 仓库：[moviepilot-plugin-colaseedgroup](https://github.com/ReelCoreHQ/moviepilot-plugin-colaseedgroup)

---

## 一、这是什么

站点有一批**官方种子**，需要有人长期挂在下载器里做种 —— 否则老种会断、下载的人拿不到速度。

**保种组就是干这件事的**：你把站点官方池按档位搬进自己的下载器长期保种，站点按月给你瓶盖奖励，保满年限后退休，保留一揽子永久权益。

### 和「辅种」的区别

| | 辅种 | 保种组 |
|---|---|---|
| 干什么 | 我**已有**的资源，去站点找同款补种 | 站点**要的**资源，我搬过来保着 |
| 谁来做 | 所有会员 | 所有会员（够 2T 进入候选池，由组长授予正式成员） |
| 有没有奖励 | 只有做种积分 | 做种积分 **+ 月度岗位奖励** |
| 有没有考核 | 没有 | 正式成员每月要保够时长 |

## 二、怎么开始（三步）

**任何已注册的站点会员都能用，不需要工作组身份、不需要审批。**

```
① 建 API Key
   https://www.colapt.com/account/tracker?tab=api
   勾「读取」+「下载」

② 填进插件
   设置 → 填 Key → 点「连通性检测」
   应显示：✅ 可乐PT：API Key 可用

③ 填下载器、选档位、保存
```

### 两种用法（同一份代码）

| 形态 | 适合谁 | 怎么装 |
|---|---|---|
| **MoviePilot 插件** | 已经有 MP | MP → 插件市场 → 添加本仓库 → 装「可乐保种组」 |
| **独立 Docker 服务** | 不想装 MP | `docker compose up -d`，面板在 **3006** 端口 |

独立版**不含** MP 的加种后自动整理/刮削/订阅 —— 那些是 MP 的职责。

## 三、档位

| 档位 | 目标体积 |
|---|---|
| 2T / 5T / 10T / 15T / 20T | 2048 / 5120 / 10240 / 15360 / 20480 GiB |
| **自定义** | 自己填，支持 `100M` `100G` `1T` `1P`（不带单位按 GiB） |
| **全站官种** | 有多少保多少 —— 目标 = 站点官方池总量，池子涨目标跟着涨 |

**「只能超，不能少」**：插件按最合适的组合挑种子，保证总量 ≥ 目标；单颗比剩余缺口还大时挑其中最小的那颗。

**只保官方种**，非官方一颗都不碰。

### ⚠ 现在只有 2T 是真能达成的

**官方池目前约 2.5T**（2560 GiB 左右）。这意味着：

- **所有人都只能落在 2T 档**（36 个月退休）
- 5T / 10T / 15T / 20T 的奖励表和退休年限，**眼下是纸面规则** —— 池子不够大，谁也到不了
- 「20T 拿不到满加成」这类说明，在池子涨到 20T 之前也没有实际影响

选 10T 不会报错，但**目标永远是「池子总量」**（全站档）或「设定值但补不满」——面板会如实显示缺口。

**池子涨上来之后**，这些档位才真正可用。

## 四、动态轮换（固定档位才有）

### 规则

| 项 | 规则 |
|---|---|
| **频率** | **每天 2 颗**（不是每轮；同一自然日跑过就不再动） |
| **能不能删** | 只删**本地做种满 3 天**的；一颗都没有就今天不删 |
| **删谁** | 站点做种人数**最多**的 2 颗（人最多 = 最不缺） |
| **补几颗** | 删完重算：**还够 → 今天不补**；**不够 → 补最缺的，补够就停** |
| **什么时候生效** | 覆盖 **≥ 设定的档位体积** |

### 「全站官种」不轮换

这个档位的意思就是**池子里有多少保多少**，要的是全保。删一颗就得再下一遍，池子永远差那几颗 —— **轮换跟这个档位的目标直接矛盾**。

所以全站档：**一颗都不删。**

> 80% 那条线是「**覆盖达标**」的门槛（达标 = 计考核、发奖励），不是轮换门槛。
> 详见第九节「月度达标」。

### 举例

**场景 A：删 2 颗大种子**

```
目标 2048，删前 2060
删 2 颗共 40 GiB → 2020 < 2048
→ 缺口 28 GiB → 补到够（可能补好几颗小的）
```

**场景 B：删 2 颗小种子**

```
目标 2048，删前 2060（余量 12）
删 2 颗共 4 GiB → 2056 ≥ 2048
→ 今天不补
```

### ⚠ 已知问题：池子贴着目标时会来回折腾

当前删掉种子后会**立刻清掉它的跳过记录**，于是下一轮它又能进补种候选 ——
如果官方池只比档位大一点（比如目标 2048、池子 2100），删掉 2 颗后能补的候选
可能就只剩刚删掉的那 2 颗，**每天删了又重下**。

**建议**（待定）：

- 刚删掉的种子 **7 天内不进补种候选**（记一条 `rotated` 跳过，与 `net`/`dup` 并列）
- 或：**池子余量**（池子总量 − 目标）低于阈值（如 50 GiB）时**跳过轮换**

### 开关：「轮换时连文件一起删」

- **勾上**：删的种子连本地文件一起删，省盘
- **不勾**：只删种子、保留文件，以后想再做种不用重下

用于腾出空间给别人补种，**不影响你已完成的下载量**。

## 五、下架清理

站点撤掉的资源（下架 / 取消官方标记），插件会从下载器里删掉它 —— **哪怕进度还是 0**。

### 文件删不删

| 配置 | 已下完（≥99.9%） | **没下完** |
|---|---|---|
| 种子和文件一起删 | 删文件 | 删文件 |
| **只删种子保留文件** | **保留文件** | **连文件删** |

**关键**：站点都撤了，本地那点没下完的文件既做不了种、又永远补不齐 —— 所以**即使配了「保留文件」，没下完的也照样删文件**。

### 文件丢了但站点还在 → 不删，救回来

如果种子还在站点、只是本地文件没了（qB 状态 `missingFiles`），插件**不删它**，而是**强制重新校验**：qB 校验后发现数据不全，会自己重新下载。

## 六、奖励措施（核心）

### 月度岗位奖励

| 档位 | 体积 | 岗位奖励/月 | 加上做种积分 | 相对 2T |
|---|---|---|---|---|
| **2T** | 2,048 GiB | **80,000 瓶盖** | 202,651 | 1.00x |
| 5T | 5,120 GiB | **217,143 瓶盖** | 368,638 | 1.82x |
| 10T | 10,240 GiB | **462,160 瓶盖** | 624,207 | 3.08x |
| 15T | 15,360 GiB | **718,932 瓶盖** | 884,551 | 4.36x |
| **20T** | 20,480 GiB | **983,648 瓶盖** | 1,151,059 | **5.68x** |

**设计意图**：体积 10 倍 → 总收益 **5.68 倍**。

站点的做种积分本身是 `arctan` 饱和的 —— 2T 到 20T 体积涨 10 倍，做种积分只多 37%。岗位奖励承担了拉开差距的职责。

### 连续达标加成

| 连续达标 | 加成 |
|---|---|
| 每满 3 个月 | +5% |
| 上限 | **+30%**（一年最多 +20%） |

### 举例

保 20T、连续达标 12 个月（加成按「每满 3 个月 +5%」逐季累加）：

```
第 1–3 月   × 1.00
第 4–6 月   × 1.05
第 7–9 月   × 1.10
第 10–12 月 × 1.15
──────────────────────
12 个月当量 = 3×1.00 + 3×1.05 + 3×1.10 + 3×1.15 = 12.9
983,648 × 12.9 ≈ 1,269 万瓶盖
```

**注意**：加成上限 +30% 要连续满 **18 个月**才到 —— 而 20T 的退休年限正好是 18 个月，
所以 **20T 成员永远拿不到满加成**。真正吃得满的是 2T（36 个月）和 5T（30 个月）。

### 发放前提

**当月「覆盖达标」的累计时长 ≥ 当月自然时长的 5/6**（约 25/30 天）。

不达标 → 当月岗位奖励不发，**但不追扣已到账的做种收益**。

## 七、退休机制

### 退休年限（按实际覆盖递减）

| 档位 | 退休年限 | 每月进度 |
|---|---|---|
| **2T** | **36 个月**（3 年） | 2.78% |
| 5T | 30 个月 | 3.33% |
| 10T | 24 个月 | 4.17% |
| 15T | 21 个月 | 4.76% |
| **20T** | **18 个月**（1.5 年） | 5.56% |

**「保得越多，退得越快」** —— 2T 要 3 年，20T 只要 1.5 年。

### 自定义档与全站档：按实际覆盖向下取最近档

**2026-11-22 已上线**（`tierMonthsFor`）。

| 实际覆盖 | 按哪一档算 |
|---|---|
| ≥ 20,480 GiB | **20T**（18 个月 / 奖励 983,648） |
| ≥ 15,360 GiB | 15T（21 个月 / 718,932） |
| ≥ 10,240 GiB | 10T（24 个月 / 462,160） |
| ≥ 5,120 GiB | 5T（30 个月 / 217,143） |
| ≥ 2,048 GiB | 2T（36 个月 / 80,000） |

原来这两档一律按 5T（30 个月），于是自定义 50T、或全站池子涨到 30T 时，
退休反而比 20T 的 18 个月更慢 —— **保得越多、退得越慢**。现在 20T 以上的覆盖都按 20T 算。

回归测试 `TestMoreCoverageNeverMeansSlowerRetirement` 钉住这条：
**覆盖越大，退休只能越快或持平，不能变慢**。

### 退休后得到什么

**移入「养老」组，13 项权限与在岗完全相同**（邀请数量有年度配额），区别只剩：

| | 在岗（工作组-保种） | 退休（养老） |
|---|---|---|
| 权限 | 13 项 | **13 项（相同）** |
| 每月保够 5/6 | **必须** | 不必 |
| 月度岗位奖励 | 拿 | 不拿 |
| 头衔 | 工作组-保种 | 养老 |

**这是刻意的设计**：在岗和为站点做过贡献的人享有同样的 13 项权限，
区别只在「还要不要每月履约」，以及退休后的邀请配额（每年 2 个）。

### 套利路径已收紧（2026-11-22）

原来有个明显的套利：**租一台 20T 盒子撑 18 个月 → 换一个终身免考核、能无限发邀请的号**。

已处理：

| 问题 | 现状 |
|---|---|
| **退休邀请不限量** | ✅ 改为**每年 2 个** |
| **在岗邀请仍不限** | ⚠ **未改** —— 在岗成员发邀请仍然无限，而 `clean` 的标准只是「30 天内登录过或有过下载/做种记录」，被邀请人登录一次就过关。买号的人登录一下就满足了 |
| **罚款与档位无关** | ⚠ **未改** —— 仍是统一 10 万，与档位/邀请次数都没挂钩 |
| **退休不进考核期** | ✅ 已纳入（2b：退休也进考核期） |

## 九、反作弊：三层防线

改插件就能白拿奖励？现在不行了。三层防线，每层单独都不够，叠起来才成立。

### 第一层：服务端算应保体积

插件报 `target_gib`，服务端**自己查档位常量表**算目标 —— 报什么数都没用。

### 第二层：服务端从 tracker 算覆盖（关键）

插件报 `covered_gib`，服务端**不信这个数**，改用 announce 记录反推：

```sql
SELECT SUM(t.size_bytes)
FROM rc_peer_sessions p
JOIN rc_torrents t ON t.id = p.torrent_id
WHERE p.user_id = ?
  AND p.last_received_at >= NOW() - INTERVAL 2 HOUR   -- 还在 announce
  AND p.last_remaining_bytes = 0                       -- 自称下完了
  AND (
        EXISTS (SELECT 1 FROM rc_completion_records c   -- 但有完成记录
                WHERE c.user_id = p.user_id AND c.torrent_id = p.torrent_id)
     OR p.downloaded_high >= t.size_bytes * 95 / 100   -- 或下载量够了
      )
  AND t.id IN (<官方池>)
```

**四个条件缺一不可**：
- 只登记了种子不算，**必须还在 announce**
- 还在下载的不算，**`left = 0`** 才算
- 不是官方种的不算
- **光报 `left = 0` 不算** —— `left` 是客户端自己报的，刷流脚本一上来就报 0 也满足前三条。所以必须再拿出「真的下过这些字节」的证据：内核库里有完成记录，或者累计下载量到了种子体积的 95%

> 95% 而不是 100%：有些客户端最后一段不算进 `downloaded_high`。

算出来的 `server_covered_gib` 才是达标判定与月度结算的依据。插件报的数字**降级为对照物**：两边差超过 5% 或 2 GiB，直接记一条 `covered_mismatch`。

### 第三层：客户端源码指纹白名单（版本统计，不是安全边界）

> **0.6.0 起这一层停用**：插件进入了「只执行」模式，不再上报 `source_sha256`。
> 历史指纹档案（`source-fingerprints.json`）保留作版本核对，本节记录的是 0.5.x 的行为。

插件每次上报带 `source_sha256` —— **整个模块源码的 sha256**。

**它挡不住蓄意修改的客户端**：哈希是客户端自己报的，改过的插件直接报白名单里的哈希就行。它只能拦住**老老实实改代码、没改上报逻辑**的人。

**真正的安全边界是第二层**（服务端从 tracker 算覆盖）—— 那一层不依赖客户端的任何自述。

这一层的实际价值是**版本统计与排查**：谁在用哪个版本、有没有人装了个非官方的分支、某次异常是不是某个魔改版导致的。

站点维护白名单 `rc_site_seed_group_clients`：

| 情况 | 标记 | 拦不拦 |
|---|---|---|
| 空指纹（老版本插件） | `client_unverified` | **不拦** |
| 白名单内且已批准 | — | 可信 |
| 白名单外 / 未批准 | `client_unapproved(sha=… v=…)` | 落库留痕 |

**为什么空指纹和白名单外都不直接拒**：拦了等于老用户一升级就掉线；而且「自己改的版本」和「还没批的新版本」在数据上分不开。先留痕，由组长在管理面判断。

### 五条行为判据

在这三层之上还叠了行为分析，都只呈现给组长看、**不自动处罚**：

| 判据 | 说明 |
|---|---|
| `covered_mismatch` | 插件报的比 tracker 算的高出 5%/2GiB |
| `tier_target_mismatch` | 固定档位却报了个对不上的 target |
| `zero_seeded` | 声称保了很多，但最老那颗才做了几分钟 |
| `no_clients` | 有客户端快照但一台都读不到（掉线） |
| `covered_jump` / `impossible_rate` | 体积暴涨且做种时长没前进／增速不可能 |

## 十、成员身份与考核

### 谁能成为正式成员

```
当前覆盖 ≥ 2048 GiB（2T），不限天数
```

达到即进入「待授予」候选池，由**工作组-组长**或 **admin** 点一下授予。

| 状态 | 能做什么 |
|---|---|
| **保种参与者** | 保种、上报、看自己的数据。**不计考核、不发奖励** |
| **保种组成员** | 以上全部 **+ 月度奖励 + 累计退休进度** |

### 月度达标

```
当月「覆盖达标」的累计时长 ≥ 当月自然时长 × 5/6
```

**「覆盖达标」按档位判定**：

| 档位 | 什么算达标 |
|---|---|
| 固定档 / 自定义 | 覆盖 ≥ 设定体积 |
| **全站官种** | 覆盖 ≥ **池子总量的 80%** |

> 全站档用 80% 而不是 100%：池子每天都在涨，要求 100% 等于永远不达标。

**80% 落到 2T 以下时怎么办**（池子 < 2560 GiB 时会发生）：

| 情形 | 处理 |
|---|---|
| 覆盖 ≥ 池子 80%，但 < 2048 GiB | **算达标**（发奖励、计进度），但**只能按 2T 档** —— 奖励 80,000、进度 1/36 |
| 覆盖 < 池子 80% | 不达标 |

> 也就是说：**达标线看 80%，档位看实际覆盖**。两个数各管各的，不冲突。
> 池子不到 2T 时，「成为正式成员」的门槛（2T）比「月度达标」的线（80%）更严 ——
> 这时全站档的人只能是参与者，进不了考核。

**月度进度按哪个覆盖算**：用**当月最后一条核验过的覆盖**（不是月内最高值）。
这样「先冲一个月 20T 再降下来」拿不到 20T 的进度 —— 月度档位取的是月末那次的档。

- 只累计**覆盖达标**的相邻上报区间
- **单段按 7 小时封顶** —— 防止长时间不上报后补报刷时长
- **覆盖量由服务端从 tracker 算**（见第九节），插件报的数字只用于对照
- 插件读不到客户端时，前 2 轮沿用上次读数 —— 这只影响**面板显示的覆盖**，
  不进入达标判定：达标读的是 `server_on_target`，它由服务端算出的覆盖决定

### 未达标的后果

| 连续未达标 | 处理 |
|---|---|
| 第 1 个月 | 站内提醒，**不清退** |
| 第 2 个月 | **移出工作组-保种**（回到「参与者」状态） |

**被清退后 3 个月内不得再申请**，3 个月后可重新申请。

**退休进度不会被清掉**：清退只移除「工作组-保种」的成员身份，
`rc_site_seed_group_standing` 里的历史进度原样保留 —— 重新申请时接着算，不是从零开始。

**邀请连带责任导致的清退也一样**：只移成员身份、进度保留。区别只在触发原因
（连续 2 月不达标 vs 被邀请人违规），后果相同。

## 十一、邀请连带责任

**你邀请的人如果「死了」，你要担责。**

### 触发条件（满足任一）

| # | 条件 |
|---|---|
| ① | 被邀请人 30 天内**既没登录、也没有任何下载或做种记录**（死号）—— 注意这个标准很松：**登录一次就算 clean** |
| ② | 被邀请人**因分享率被封禁** |

### 判定窗口

**只判定被邀请人进场后的 30 天内**（`due_at = 激活时间 + 30 天`）。

- 30 天后才不玩的，**不追溯** —— 几年前邀请的人现在退坑，与邀请人无关
- **历史邀请一律不追溯**：规则上线前产生的邀请，`pending` 行统一收尾成 `skipped`，
  sweep 不会再碰它们（否则第一次扫描会把几年内的老邀请一次全判）
- 每条邀请**只判定一次**：状态机 `pending → clean / dead / ratio_banned → penalized`，
  终态不再重判，所以**同一个被邀请人不会重复罚款**

### 处罚（针对邀请人）

| 步骤 | 动作 |
|---|---|
| 1 | 扣 **100,000 瓶盖**（余额允许为负） |
| 2a | 你在保种组 → **立即清退**，账号进入 **1 个月考核期** |
| 2b | 你在**退休组** → **不清退**（本来就不在保种组），但**一样进考核期** |
| 2c | 两者都不是 → **只扣款**，不考核 |
| 3 | 考核期满**余额仍 ≤ 0** → **封号** |

### 两个点的现状

| 问题 | 现状 |
|---|---|
| **2a 过重** | ✅ 清退只移除成员身份，**不动退休进度**（见第九节说明） |
| **余额藏欠款** | ⚠ 账本已允许负数（`CreditOverdraft`），但**前端仍显示 0** —— 待改 |

## 十三、常见问题

**我保到了 2T，为什么还没奖励？**
覆盖达标只是进入「待授予」候选池，要等**组长或 admin 授予「工作组-保种」**之后才开始计考核、发奖励。

**我不是工作组成员，能装插件吗？**
能。任何会员都能装、能保、能看自己的数据，只是不计考核、不发奖励。

**我是全站官种，为什么从没轮换过？**
**全站档本来就不轮换** —— 这个档要的是全保，删了补不回。轮换只对固定档位生效。

**显示缺很多，但站点明明有那么多官种？**
插件只保**官方**种。官方池本身小于档位时，如实显示缺口 —— 这是事实。

**我的覆盖突然变成 0 了？**
看面板上的标记。如果是「掉线」，说明连续 3 轮读不到你的下载器（网络问题或 qB 挂了）。偶发 1-2 轮失败会沿用上次读数，不会归零。

**想用 MP 的整理/刮削？**
用插件形态。独立 Docker 版刻意不含这些。

**退休后还能保种吗？**
能。权益全部保留，只是不再有月度义务和奖励。
